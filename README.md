# Project Brand Kit & Identity Guidelines

## Brand Overview
* **Project Name:** IRONBOUND

IRONBOUND is a gritty post-apocalyptic cooperative survival game set in a world where nature has begun reclaiming the remains of human industry. Its visual identity balances decaying rail infrastructure, rusted machinery, and environmental danger with the beauty of forests, open skies, snow, and overgrown landscapes.

The brand should feel industrial, weathered, atmospheric, and resilient. Human-made structures should appear worn and fading, while vegetation and natural lighting should communicate that the world continues beyond the collapse.

## Logo

Use the IRONBOUND logo consistently across the game, repository documentation, marketing materials, presentations, and project-related media.

### SVG Files

  * [Black logo](./branding/logo/black/logo_black.svg)
  * [White logo](./branding/logo/white/logo_white.svg)

### PNG Files

  * [Black logo](./branding/logo/black/logo_black.png)
  * [White logo](./branding/logo/white/logo_white.png)

### Logo Usage
- Use the black logo on light backgrounds, including Mint Cream, Larimar, and other light environmental artwork.
- Use the white logo on dark backgrounds, including Racing Green, Blue Sapphire, Dried Blood, and dark gameplay scenes.
- Preserve the logo’s original proportions. Do not stretch, rotate, crop, recolor, or add effects that reduce legibility.
- Leave clear space around the logo so it remains readable and visually distinct from surrounding text or artwork.
- Use the logo at a size where the title remains legible in both digital and printed materials.

## Color Usage Guidelines

- Use **Blue Sapphire**, **Sienna**, and **Seal Brown** as the primary industrial-material colors.
- Use **Racing Green**, **Growth Green**, and **Kariyasu** for landscapes, vegetation, and natural terrain.
- Use **Mint Cream** for high-contrast light text and environmental highlights.
- Use **Larimar** sparingly for clear skies, bright lighting, water, and non-critical informational UI elements.
- Reserve **Dark Red** for urgent warnings, damage states, danger, and fresh blood.
- Use **Dried Blood** for older stains, grim environmental details, and subdued danger imagery.
- Avoid using every palette color in a single interface or asset. Prioritize readability, visual hierarchy, and the intended mood of the scene.

## Typography

IRONBOUND uses two primary typefaces to create a contrast between harsh industrial branding and readable in-game information.

| Font | Use | Guidelines |
|---|---|---|
| **Impact** | Game title and major display text | Use for the IRONBOUND title, logo-adjacent headings, title screens, and major promotional material. Use sparingly so it retains impact. |
| **Syne Mono** | In-game text and interface typography | Use for HUD text, menus, dialogue interfaces, item descriptions, system messages, documentation callouts, and technical or industrial-themed UI elements. |

### Typography Rules

- Use **Impact** primarily for large display text, not body copy.
- Use **Syne Mono** for readable in-game interface text and technical-style labels.
- Use sentence case or title case for headings based on the relevant UI or document context.
- Avoid excessive all-caps text outside of the game title, urgent warnings, and short UI labels.
- Maintain sufficient contrast between text and its background, especially in dark or visually busy scenes.
- Do not substitute decorative fonts that conflict with the industrial and post-apocalyptic visual direction.

## Brand Identity Standards

### Tone and Atmosphere

IRONBOUND should communicate a harsh but visually striking post-apocalyptic world. The game should emphasize the contrast between abandoned human infrastructure and the resilience of nature.

Core identity traits include:
- **Industrial:** Rusted trains, machinery, rail lines, warning lights, metal structures, and damaged equipment.
- **Post-apocalyptic:** Abandoned environments, signs of collapse, worn materials, remnants of past human activity, and environmental hazards.
- **Natural reclamation:** Forests, overgrown railways, vines, grass, snow, water, and sunlight reclaiming industrial spaces.
- **Gritty:** Weathered surfaces, muted materials, blood, dirt, decay, and a sense of danger.
- **Atmospheric:** Strong lighting, open skies, fog, shadow, contrast, and environmental storytelling.
- **Resilient:** The world is dangerous and deteriorated, but it is not lifeless; nature and survivors continue to endure.

### Visual Direction

- Favor worn, practical, and believable materials over clean futuristic designs.
- Show evidence of age, use, weathering, and neglect on human-made structures.
- Contrast dark industrial settings with natural greens, bright skies, snow, or warm sunlight.
- Use rust and oxidation as visual indicators of abandoned machinery and railway infrastructure.
- Use blood and red warning colors intentionally, not decoratively, to preserve their association with danger.
- Keep UI elements functional and legible while reflecting the world’s industrial character.
- Avoid overly polished, neon-heavy, cartoonish, or sterile visual treatments unless they serve a deliberate gameplay purpose.

## Brand Summary

IRONBOUND combines post-apocalyptic industrial decay with the quiet beauty of a world reclaimed by nature. The project’s visual identity should consistently communicate danger, survival, machinery, weathering, and environmental resilience while keeping the game readable and approachable for players.

# Contribution Guide

This guide defines the workflow standards for contributing to **IRONBOUND**. All significant work should be tracked through a GitHub issue, completed on a dedicated branch, reviewed through a pull request, and merged into `main` only after approval.

## Repository Workflow Standards

1. Create or select a GitHub issue before starting significant work.
2. Create a short-lived branch from the latest `main` branch.
3. Make focused commits using the required commit format.
4. Open a pull request linked to the related issue.
5. Request review from at least one team member other than the author.
6. Resolve review comments and ensure required checks pass.
7. Squash-merge the pull request into `main`.
8. Delete the branch after merging.

Direct commits to `main` are reserved for repository initialization or urgent recovery situations agreed upon by the team.

Work is complete when its acceptance criteria are met, relevant tests and documentation are updated, review comments are resolved, a non-author approves the pull request, and applicable AI use is documented in [`AI_LOG.md`](./AI_LOG.md).

## Branch Naming Conventions

Use lowercase kebab-case branch names so branches remain readable and easy to find.

### Format

```text
<type>/<issue-number>-<short-description>
```

### Examples

```text
feature/42-route-planning
fix/17-login-validation-error
docs/12-market-feasibility
refactor/28-ai-log-service
chore/9-update-dependencies
test/33-route-planning-tests
```

### Rules

- Use lowercase letters and hyphens between words.
- Start with a branch type followed by `/`.
- Include the related GitHub issue number.
- Keep the description short and focused on one change.
- Do not use spaces, underscores, or unrelated issue numbers.
- Create new branches from the latest version of `main`.

### Branch Types

| Type | Use for |
|---|---|
| `feature` | New features or player-facing capabilities |
| `fix` | Bugs or unintended behavior |
| `docs` | Documentation and project standards |
| `refactor` | Code restructuring without behavior changes |
| `test` | Adding or updating tests |
| `chore` | Tooling, configuration, dependencies, or maintenance |
| `hotfix` | Urgent fixes |
| `release` | Release preparation |


## Commit Message Formats

Use Conventional Commits for all commit messages.

### Format

```text
<type>(optional-scope): <imperative summary>
```

### Examples

```text
feature(routes): add station selection
fix(inventory): prevent duplicate item stacks
docs(brand): define primary color palette
refactor(ui): simplify pause menu state handling
test(routes): add station selection test cases
chore(deps): update dependencies
```

### Commit Rules

- Use lowercase commit types.
- Write summaries in imperative mood, such as `add`, `fix`, `update`, or `remove`.
- Keep each commit focused on one logical change.
- Do not end summaries with periods.
- Avoid vague messages such as `updates`, `fix bug`, or `WIP`.

| Type | Use for |
|---|---|
| `feature` | New functionality |
| `fix` | Bug fixes |
| `docs` | Documentation |
| `refactor` | Code restructuring |
| `test` | Test changes |
| `chore` | Maintenance and tooling |
| `ci` | GitHub Actions or CI changes |
| `perf` | Performance improvements |

## Pull Request Procedures

All significant changes must be submitted through a pull request before merging into `main`.

### Pull Request Template

```md
### Description:
*Provide a clear summary of what this PR does and why.*

- 

### Type of Change:

- [ ] New feature
- [ ] Bug fix
- [ ] Refactoring (no functional changes)
- [ ] Documentation update
- [ ] Infrastructure / CI/CD
- [ ] Performance improvement

### Changes Made:
*List the specific changes. Be precise.*

1.
2.
3.

### AI Usage:
*Add log number from `AI_LOG.md` file. Remove section if no AI was used.*

- Log #<log-number>

### Related Issues
*Link related tickets or issues. Use "Closes #<issue-number>" to auto-close.*

- Closes #<issue-number>
```
